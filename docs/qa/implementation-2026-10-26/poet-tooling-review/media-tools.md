# Poet media and creative tool reuse review

**Read-only source review · 2026-10-26.** This addresses the direction that the MIT/Apache-2.0 Poet-* suite offers reusable capability beyond CAD. It examined public workspace exports/catalogues broadly, product architecture summaries, and selected implementation bodies. No product source was moved or edited; no build, test, Cargo, provider, runtime, or GUI operation was run. Exact selected source files/ranges and SHA-256 pins are in [coverage](media-tools.coverage.json). Each app root `Cargo.toml` declares `MIT OR Apache-2.0`; each inspected root includes `LICENSE-MIT`, `LICENSE-APACHE`, and `NOTICE`. This confirms the repositories' declared dual-license option, not legal advice or file-by-file provenance. Preserve applicable MIT notices and attribution when reusing files; review dependencies and notices at extraction.

## Product conclusion and evidence levels

The five tool families contain substantial engines, document models, histories, codecs, render/export paths, automation and interaction patterns. The target is to refactor reusable MIT-licensed capabilities and useful editing/UI behavior into Poet as internal functionality, preserving required notices and existing Poet behavior, as required by the governing [Poet/Craft plan](../../../planning/tech/poet-craft-consolidation.md). The earlier `C:/github/craft` layout is a historical extraction proposal to reconcile per library with current source homes; a blanket folder move is neither the product outcome nor a prerequisite for each usable authoring slice. Their existing standalone shells are migration references. No source relocation or native Poet wiring is demonstrated by this audit. Source present, current Poet consumed, and accepted native production workflow are three distinct states. The existing Poet architecture reference has tool chest, manifolds, menus, content containers, stage/timeline, inspector and Vibe/intent concepts; domain controls should project into this established unified authoring environment rather than become a collection of independent authoring applications.

The product direction is wider than CAD: photo raster editing and capture development; vector illustration/diagram and 2D plates; multitrack sound; timeline editing, compositing, grading, captions and media export. These functions strengthen a native cooperative authoring suite, but do not alone provide the missing integrated organic 3D modeling/rigging/HMC chain identified in the production-toolchain specification. A screenshot, source API, CLI, MCP tool, or isolated renderer does not prove contributor/reviewer source-to-output work under IP-03 C1–C8.

## Revised disposition

This review updates any CAD-only description of reusable Poet suite capability: the five inspected media families are real source reuse candidates and their authoring UX contains useful patterns to preserve. It does **not** close TOOL-01/02 or IP-03 C1–C8: there was no current Poet-to-tool invocation, native graphical cooperative edit, reviewer flow, cross-tool stable document/selection/undo contract, output reopen, or acceptance run. The larger production-toolchain limitation remains accurate: a complete integrated film-quality organic modeling/rigging/HMC workflow was not established by these media-tool findings. Future implementation allocation should first map each required production case to existing tool/document APIs and owner, then build Poet-integrated controls and cross-domain provenance only at demonstrated seams. No new media engine or generic gap is justified by this bounded review alone.
