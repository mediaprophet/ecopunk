# UI4: explicit geometry execution rebuild and epoch guards

Staged on 2026-10-25 under the continuing 2026-10-24 batch. UI3 evidence remains historical and unchanged. Its exact three proposed source byte snapshots are preserved and hash-verified in `ui3-originals/`; the candidate paths now contain this subsequent UI4 proposal.

This task owns only `candidate/native/src/graphical/{mod.rs,ui.rs,jobs.rs,jobs_tests.rs}`. The controller, opaque `SessionEpoch`, actual two-operation `GeometryHost`, bounded source-history rebuild, preview adapter, native entry, manifest and guarded application remain the native integration owner's work. UI4 calls that explicit provider contract; it adds no generic source replay, session cloning or durable recovery mechanism.

The UI exposes **Rebuild execution session** only when the current actual host snapshot reports `rebuild_supported`. It is enabled when reconciliation is required. The explicit command captures the source stamp and complete originating execution context. It calls `EditorHost::rebuild_execution` once on the owned worker. It does not submit the draft, replace a dirty draft, rebuild automatically after Undo/Redo/errors, or automatically retry/resubmit afterward. Unsupported hosts have no displayed rebuild control; a direct internal request fails before provider dispatch.

Every job context now includes the source identifier plus opaque incarnation/revision stamp, numeric Vibe session revision, opaque execution epoch, and reconciliation flag. Frames retain the exact corresponding outcome context through image encoding. The derived completion cache is invalidated while each job runs, then updated from the actual resulting host snapshot. This cache is a small completion guard, not a second owner of project/session state. The UI uses a nonblocking cache read, the resulting epoch's live flag and the actual store's cheap nonblocking stamp check immediately before publication. Thus a previously sent success cannot publish after a failed attempt holds the session without changing its numeric revision, and an old queued request/reply/frame cannot publish across a rebuild that restarts the same numeric revision with an unchanged source stamp. Successful rebuild intentionally retires the *originating* epoch; the origin still matches the old displayed view by identity, while the resulting epoch must be current. Refresh can therefore recover a stale displayed context.

The same single native worker and one queued request remain. Close stops admission, cancels not-started work, and joins started work. Started rebuild/native operations are never detached or falsely reported cancelled. Source/host effects are not automatically retried.

Eleven focused CPU tests are staged in the separate test module, including repeated-revision epoch changes, prior-success rejection after a held-state transition, mismatched preview epoch, unsupported rebuild, and joining a started rebuild while cancelling a queued command. Rustfmt completed. These tests have **not** been executed by the UI task. The integration owner will run the coherent actual native build/tests; positive tests should run with `--test-threads=1` because the actual store's nonblocking guard deliberately fails closed under unrelated concurrent global-store contention. This is not evidence of completed multi-contributor UI cooperation.

The existing geometry prepare-only probe and the frozen canonical runtime receipt remain unchanged. No native window, rebuild engine execution, HMC/material authoring, durable cooperative recovery, complete embodiment, high-grade master or Vibe 0.2 acceptance is claimed by this staging note. The preview remains a factor-material SDR working view. See `ui4-staging.json` for exact proposed source hashes and historical evidence pins.
