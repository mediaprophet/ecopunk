## Identity and key APIs

- `C:/github/qualiaDB/crates/qualia-client-core/src/identity_plane/person.rs:15-45` defines `PersonPrincipal` with `did:q42:person:{verifying_key_hex}`, a raw Ed25519 signing secret, and public projection/transfer types. `:71-96` selects the wrapping key: live unlocked KeyVault derivation under `person_identity_v1`, otherwise an app-meta local `person_wrap.key` (not OS account/keyring). `:100-143` provides `signing_key`, public-key projection, DID derivation and generation. `:146-204` loads or creates identity, decrypts sealed `qualia.person.sealed.v1` with `PERSON_AAD`, accepts legacy plaintext and migrates it by persist. `:206-244` seals on persist and signs/verifies messages; verification checks DID equals the supplied verifying key, then Ed25519 verifies. `:238-254` replacement checks that DID matches the signing secret; transfer import persists the bundle.
- The implementation exposes secret-bearing `PersonPrincipal` fields and `signing_key()` publicly, and transfer bundles contain the whole principal (`person.rs:18-20,44-45,101-103,244-257`). A UI adapter should keep this owner-side and pass only the digest/signature; do not serialize/log/render the principal or transfer bundle. `load_or_create` silently mints on first run, so it is suitable for local identity bootstrap but not evidence that a person is enrolled in a project.
- `C:/github/qualiaDB/crates/qualia-core-db/src/identity/key_vault.rs:110-162` owns `KeyVault`, lock state and native `load_or_generate` (OS keyring preferred, `keystore.bin` fallback); wasm has a separate filesystem-backed implementation at `:219-252`. `:254-290` derives purpose-separated role keys and allows host-only role-seed requests while unlocked. `:299-329` signs payloads and verifies signatures. Its root/context keys are distinct from PersonPrincipal's Ed25519 identity key: person persistence derives a wrapping key; the user/controller proof API expects a public key already bound in the signed project subject admission.

## Project adoption, key possession, and session

- `C:/github/qualiaDB/crates/qualia-core-db/src/poet_host/native_authority/mod.rs:43-60` defines opaque `SessionHandle` and `SessionChallenge` (no `Deserialize`; digest accessor only). `:85-153` opens `NativeAuthority` using a supplied `TrustedProject` anchor and `SignedAdmission`; it verifies the signed admission and project/source binding and retains durable records. `:155-180` only accepts a fresh higher-sequence replacement signed by the pinned project authority, invalidating pending/live sessions.
- `.../native_authority/session.rs:4-57` begins a session only for an unrevoked/current subject in that signed admission and creates a fresh nonce-bound digest tied to authority incarnation, admission digest, controller key, project, subject, and expiry. `:59-134` consumes the one-use challenge, checks owner/nonce/digest/expiry/current admission, verifies Ed25519 using the admitted controller public key and `SESSION_CONTEXT`, then installs a current QDNF grant and issues a nonserializable session handle. `:136-150` revokes on disconnect. The caller must produce the QDNF context-bound signature over `challenge.message_digest()` using the admitted controller private key. `PersonPrincipal::sign_message` alone is incompatible because it signs raw bytes; the matching helper is `crypto/network/ed25519.rs:11-24` (`sign_with_context`, with exact `SESSION_CONTEXT`). Check visibility across crate boundaries before wiring; an additive qualified helper may be required. The admission must bind that person's verifying key to the subject.
- `NativeAuthority` does not discover/adopt projects or enroll a human. The native host must supply a trusted project anchor and current signed admission records. A successful challenge proves control of the private key bound in the adopted admission at that time. The signed project admission separately carries subject identifiers, membership, review grants, validity and revocation; it is project authority's assertion. A matching DID/string or successful proof does not itself prove personhood, legal identity, contributor/reviewer qualification, actual role performance, or human acceptance. Qualification needs its own authoritative evidence and issuer/validity policy.
- Batch-4 `authentication/README.md` confirms the integration contract remains open for real adopted trust anchors, current signed admissions, contributor/reviewer key enrollment/signing integration and usable GUI acceptance; existing tests are fixture evidence, not real-human enrollment.

## Poet launch and integration seam

- `C:/github/poet/native/src/main.rs:15-27,39-54` exposes CLI commands; with `native-graphical`, `studio` calls `graphical::entry::run`. `entry.rs:1-3,156-242` explicitly labels that path local diagnostic. It constructs diagnostic URIs/artifact/source session from CLI-selected grants, mentions no PersonPrincipal/KeyVault/NativeAuthority/SignedAdmission/session, and rejects launch without the diagnostic profile (`:30-85,156-242`). It cannot be promoted into production enrollment by changing the diagnostic label.
- `C:/github/poet/native/src/graphical/native_project.rs:22-40` defines a host-supplied config; `:44-138` opens the canonical editor under caller-supplied `NativeAuthority` and `SessionHandle`; `:140-173` reconnects and exposes the same authority/session to UI, MCP and main-thread native Aether. This is the production reuse point after native admission and possession proof. UI/Poet code should not mint session handles or accept project/member/reviewer authority from CLI/MCP fields.
- `ui.rs` and `jobs.rs` are editor/projection/job lifecycle owners, not identity or enrollment providers. They carry source/session revision guards. Keep their authoring model and pass an already authenticated native host/session into existing NativeProject/launch route.

## Native/WASM boundaries and practical constraints

- PersonPrincipal persistence uses `std::fs` in this module, and its wrapping-key fallback writes `person_wrap.key` in app-meta (`person.rs:71-96,146-204`); `KeyVault` uses native keyring under `cfg(not(target_arch="wasm32"))`, with a separate wasm file implementation (`key_vault.rs:13-18,162-252`). This is not evidence of a browser-safe credential storage or user-gesture signing flow. Native proof integration can reuse the native owner APIs; WASM/browser needs a separately qualified binding/storage boundary and must not claim native key isolation based on these APIs.
- SessionHandle/Challenge must stay process-local/opaque; challenge is one-use and current admission is rechecked on operations. On adoption replacement, expiry, revocation, disconnect or process restart, reacquire proof/session through current owner state rather than restoring a serialized handle.
- Avoid importing sibling logic into Ecopunk: Poet and QualiaDB own these APIs in their repositories. The Ecopunk inventory is evidence/handoff only; actual integration writes need the separately authorized owning repository/specific file assignment.
