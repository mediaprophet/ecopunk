## What already exists

- **Native geometry operators:** `poet/native/src/graphical/spatial_host.rs` projects bounded Vibe inputs to `poet_spatial_authoring` operators, currently profile sweep, UV sphere and torus; `geometry_host.rs` applies capability checks and explicit dispatch/work/vertex/scratch/profile budgets. `crates/spatial-authoring/src/geometry.rs` implements profile sweep, sphere and torus. This is usable operator/kernel plumbing, not proof of graphical access or a full geometry toolset.
- **Assemblies and TRS:** `crates/spatial-authoring/src/assembly.rs` defines `Transform {translation, rotation, scale}`, validates finite values/positive scale, and compiles identified parts with mesh/material/UV/normal/frame data. `native/src/graphical/assembly/admission.rs` admits Vibe assembly records and TRS fields; `assembly/render.rs` previews; `assembly/compile.rs` emits `.10d` using Core mesh+frames, UV and material-section attachment APIs. Native `authoring/controls.rs` exposes part inspection and source edits, and `authoring/controller.rs` invokes the compiler. This is existing source-to-.10d/HMC functionality: the UI explicitly offers “Compile accepted assembly into HMC”; controller pins source and compiled digests and produces a Core `CompiledAsset`; authenticated work routes through Poet's existing intent bus. This does not establish executed GUI usability. The flattened `.10d` derivative does not itself encode source assembly graph/TRS/membership; source and Q42 lineage need to remain in the HMC/package side.
- **Material authoring:** `materials.rs` admits explicit linear base-color/emissive and scalar factors into Core `MaterialRecord`, rejects unverified texture bindings, and supports authored source drafts. `material_controls.rs` stages Vibe source; `material_edit.rs` validates the constrained source edit while retaining source as authority. This supports factor-only material edits and the MAT4-compatible section projection; textures/physical material data are deliberately unavailable here.
- **Current Core `.10d` API:** `render/compile_10d.rs::compile_mesh_to_10d_with_frames`; `container_10d::attach_texture_coordinate_section`, `attach_material_section`, `encode_container`, and `parse_section_table`; typed identity helpers `encode_container_with_manifold_identity[_extensions]` / `decode_container_manifold_identity`, `ManifoldIdentityV2` and `StableEntityId`; `TypedPayloadResolver` for manifest-linked typed fields, surface frames and morph targets. Separate field codec APIs include `encode_field_section_with_rasters` and `decode_field_raster_samples`. These are existing candidate APIs; none is evidence that Poet currently composes all of them into a semantic master/HMC save.
- **Existing checkpoint preservation:** Poet has checkpoint/HMC resource-preservation paths in `graphical/checkpoints` and `native_project`; earlier RUN09/RUN10 records in batch-4/5 describe broader package/source retention. The authoring UI states retained resources survive compilation and the compiler binds output to source/compiled digests. I did not re-audit checkpoint implementation or execute the complete path here, so persistence/reopen and semantic identity/graph lineage remain unverified in this inventory.

## Priority gaps / recommended follow-up

1. **P0 — qualify existing source-to-HMC route and close semantic-lineage gap:** use the existing “Compile accepted assembly into HMC” control and authorized Poet intent/checkpoint path, then demonstrate saved HMC reopen with source, resources and `.10d` in one identified package. Controller computes source/compiled digests and Core `CompiledAsset`; this source path exists. Remaining evidence is execution/reopen and explicit preservation or refresh of qualified referent identifiers and source-to-derivative lineage. `assembly/compile.rs` emits geometry/UV/material but does not attach MID2 or Q42 assembly graph itself.
2. **P0 — preserve semantic assembly rather than drawing-only flattening:** retain stable part identifiers, membership/parent, attachment frames, units, and design/instance/representation distinctions in Q42/HMC alongside flattened render derivative. Current `CompiledAssembly` projection has part IDs/TRS, but `compile_assembly` folds parts into one mesh and loses graph/TRS in the `.10d` bytes. Follow made-world REQ-MADE-001–005; do not treat a mesh ID or local record key as universal identity.
3. **P1 — finish material/source linking:** native UI's factor controls stage source, but material ID allocation/revision and persistent link between source declaration and MAT4 section need a clear owner/update contract. Textures require verified bytes, roles/color-space and resource lineage before admitting; physical properties need distinct typed sourced data, not visual factors. Existing Core MAT4 attachment is reusable; no basis to call whole materials capability absent.
4. **P1 — qualify TRS controls and semantics:** native controls already inspect/edit parts and expose translation/rotation/scale source edits through the shared session. Source inspection alone does not prove usable editing, precision/units, or human contributor/reviewer workflow. Confirm stated units/conventions and round-trip saved/reopen behavior, including stale-source cases.
5. **P2 — typed `.10d` composition and conformance:** determine whether master assembly output should combine mesh, frames, UV, MAT4, MID2 and any relevant FIEL/MRP sections in one container; use typed section APIs and preserve/reject opaque data under established rules. Existing assembly compiler produces core mesh+frames+UV+MAT sections, but no MID2/typed sidecars. Explicitly keep format compatibility and unknown preservation contracts.
6. **P2 — interface/usability qualification:** provide actual native Poet contributor and reviewer paths through graphical controls, source-to-output review, errors, and saved/reopened master. The code inventory cannot establish human usability, native no-JS runtime, or IP-03 C1–C8. No new JS/V8 authoring dependency is warranted.
