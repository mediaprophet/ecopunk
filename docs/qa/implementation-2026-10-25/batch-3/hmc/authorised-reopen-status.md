# Fresh native checkpoint reopen authority followup

The staged `poet-reopen-candidate/checkpoints/authorised_reopen.rs` provides a fresh-source admission path that does not assume Studio already contains the source. It uses the existing trusted `AuthorityOwner`, `Scope`, `GatewayLimits`, public native `source_digest`, and core `AuthoringAction::ReopenCheckpoint` policy. It does not add an authentication provider, source-facing principal/grant loader, private role map or cross-owner transaction.

Before authority lookup it checks exact service project/document/source/domain binding and prepared source identifiers/domain against the host's trusted Scope. Under the provider's one current-state callback it authorizes the current native document, requires that document's revision and digest to equal the bounded inert prepared source, and calls the existing service's final disk-digest reread and atomic create-if-absent activation. No source runs on load, no existing source is replaced and a newly opened interpreter remains held. The callback is consumed once; duplicate invocations never repeat activation. A provider error after callback execution explicitly reports that activation may already have committed and reconciliation is required. Persistence of the admitted native DocumentRevision/proof and actual authentication remain provider responsibilities.

`poet-reopen-followup-manifest.json` freezes three exact targets against actual post-apply source: the existing checkpoint module route plus two additive files. Earlier manifests, original candidates and parent apply receipts are preserved. `authorised_reopen_tests.rs` stages focused negative cases for an unbound owner and a foreign project Scope, using actual saved/prepared HMC state and checking that the prior source and runtime stamp are preserved. These tests are fixture evidence only and have not run. No build or sibling edit was performed by this worker. Root owns guarded apply and actual native library qualification.
