## 1. Why the output is poor despite substantial engine work

The inspected chain contains **content and integration failures sufficient to
prevent high-quality output even with a capable GPU stack**. The graphics audit
and its captured frames support the observations below. Exact deployed/local
byte identifiers and the dominant cause of the washed-out image remain unverified.

| Evidence | Consequence / work allocation |
|---|---|
| Audit G01/G03: wrong texture-role admission; bark applied to fauna; pebbles shared by person/vehicle; four small colour maps standing in for distinct surfaces. | Repair semantic assignments, resource bindings and authored surfaces. A new GPU backend cannot infer skin, fur, rubber, glass or cloth from those inputs. ECO-051–060. |
| G04–G06: opaque canopy cores, oversized leaves, archetype cycling, tube/ellipsoid anatomy. | Author diagnostic form, topology, foliage and deformation. More samples or polygons alone do not establish a finished subject. ECO-061–090. |
| G10/G11: stale metadata and separate stored/generated/native/browser content routes; the visible browser path does not load the reviewed model set. | Establish one versioned source-to-HMC-to-runtime path and prove the exact representation is used. Improving an unused asset does not improve the frame. ECO-021–030. |
| G02/G07–G09: different native/browser look settings, synthetic terrain under place labels, inconsistent transforms, obstructive UI/cameras. | Calibrate presentation, use truthful place data and units, and frame the content. ECO-005/051/091–100. |
| G12: rebuild/reload on interaction and repeated vertex work; cost unmeasured. | Profile actual work and fix ownership/update paths; do not attribute slow interaction to the GPU library without evidence. ECO-086/099/101–110. |
| Present templates/gates are specifications; meshes, shader counts and source presence have been used as stronger evidence than they establish. | Require content review, active-path proof and complete deliverable claims. ECO-001–020/111–120. |

Etalon has concrete extensions and consumer integration source, and historical
trackers report extensive completed work. [The handoff](etalon-capability-handoff.md)
records both. The missing evidence is **which qualified capability and which
reviewed content the actual delivered artifact uses**, followed by the remaining
outcome-specific gaps. Universal superiority is neither established nor a
prerequisite for producing a good reference model and scene.

**Next implementation batch:** bind the M0 decisions and visual targets; identify
the actual dependency/artifact path; repair metadata and content routing; render
a diagnostic material/light fixture natively; connect an editable authoring path;
then deliver high-grade tree and animal masters beside vehicle/person scale
anchors in a reviewed place composition. Derive and review the game versions
and show the same identified content in the bounded civics case. Do not start
by adding another renderer or increasing
every primitive's polygon count. Resolve a demonstrated missing shared capability
in its owning dependency when that batch exposes it.

P0 = decision, correctness or evidence blocker. P1 = required reference-production
work. P2 = broader coverage/scale after the reference path; it remains required
where the product/subject scope calls for it. Dependencies are packet IDs for
scheduling, not assertions that the prior implementation is missing. A task may
close by proving an existing capability satisfies its acceptance without new code.

Instantiate repeated packets by subject, target and milestone. Dependency edges
must be satisfied for those identified cases: the reference tree does not wait
for all species in ECO-069, nor the reference scene for every future capacity
case in ECO-109. A milestone may pass its selected cases while the parent packet
remains in progress with broader cases open. A packet is verified complete only
when its entire allocated case inventory passes. Inventory completeness itself
requires review; empty/unassessed case arrays cannot establish zero obligations.

## 15. Claims and closure for this list

For **every ECO packet**, maintain status, actual owner/reviewer, requirement
baseline, exact changed scope, concrete result, evidence/artifact references,
remaining cases, decisions and the next dependency. Allowed working statuses:
open, in-progress, blocked, claimed-complete-awaiting-review, verified-complete.
“Already implemented” is a source/evidence observation, not automatic closure;
reused valid proof can close its qualified scope without rewriting working code.
The [starter packet ledger](ecopunk-production-claims.template.json) begins with
all 120 packets open and no claimed results/reviews; copy it into the actual
production record and keep its requirement digest current. It is not a new
runtime authority or an installed validator.

Every **model** separately needs the [193-deliverable template](assets/model-production-template/README.md),
expanded inventories and claims under the existing completion contract. Every
applicable movement, transition, behaviour, part, representation and scenario is
an obligation; 193 base rows are not a fixed upper bound. Scope reduction,
unavailable tooling and self-awarded approval cannot close a package. A scene
milestone may be accepted while its incomplete species/thing dossiers remain
explicitly incomplete.

Existing S/A/I/P/E/Q, G1–G89, PC, TOOL, ENV and CHORA IDs retain their own status
and acceptance. ECO closure must link applicable detailed IDs and cannot silently
retire them. Stage priority does not waive target/quality/domain completeness.
Specification work being complete does not close implementation packets.
