# Source-compatible stale viewport pick guard — staged only

The earlier representation-field candidate would add required fields to public `ViewportState`, breaking external Rust struct-literal consumers. It is superseded and must not be installed without an explicit migration. The current canonical viewport remains unchanged by this worker.

This single-file candidate preserves all public interfaces and ordinary orbit, pan and zoom paths. It records the existing renderer's `frame_id` when the pointer goes down. Before using a click and again after asynchronous element-layout measurement, it requires the same frame, source, execution epoch and authorization/session context. A rig-pose render or restore produces a new frame even if the source is unchanged; the click is refused instead of being retargeted to that new image. The renderer independently checks the supplied frame ID when executing the actual pick.

The staged unit test exercises the actual guard with an accepted source and context, including same-frame acceptance, no-frame refusal, same-source pose/restore frame changes, a different execution epoch and different source. Existing signed GPU rig test `native_project_rig_tests.rs` already checks stale frame rejection and disconnected authority; this candidate does not alter that fixture. No Cargo, GPU, Dioxus event dispatch or human UI test has run. Exact source and candidate SHA-256 are in `manifest.tsv`.

Limitations: this does not implement full mode-aware queued drag/zoom semantics or a botanical normal preview. The public viewport currently has no representation-mode token, and an internal UI sidecar cannot reliably observe other actors' viewport changes. Treating every changed frame as a different mode would also discard ordinary coalesced camera motions. A complete mode-aware gesture identity requires either an explicit public API migration or another authoritative host token, with compatibility and behavioral tests. This limited change does not modify `ViewportState`, source, HMC or topology.
